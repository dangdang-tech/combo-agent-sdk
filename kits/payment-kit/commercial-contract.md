# 套餐、业务点数与收款合同草案

本文件是 [Combo #357](https://github.com/dangdang-tech/Combo/issues/357) 的实现输入，不新增或改变现有 `/v1/payments` 合同。以下规则描述要实现的行为；示例配置保持 `draft`，平台尚未提供本 kit 的导入或发布接口。

## 配置约束

最小范围为一个创作者、一个 Agent、一种币种、一个支付渠道和至少一个套餐。点数先限定在该创作者和 Agent 内，余额按已验证用户、创作者、Agent、点数单位隔离；不能把现有全局人民币钱包直接改名成点数钱包。

| 配置 | 必须表达的含义 |
| --- | --- |
| `creatorId` / `agentId` | 受权限控制的收费归属。配置标识不是身份凭证；发布时必须校验操作者有权管理且收款主体已核验。 |
| `catalogVersion` | 不可变的价格版本。变价发布新版本，保留历史；订单与消费冻结所用版本。 |
| `money` | 当前示例仅 CNY、最小单位为分。金额是正整数，不能用浮点元数记账。 |
| `packages` | 套餐 ID、价格分数、购买点数、促销点数。到账点数为两类点数之和，但账本分开保存。 |
| `services` | 服务 ID、一次业务动作扣点数量。允许 0 点免费服务；收费单位是 `business_operation`。 |
| `trial` | 是否发放由 0 或正整数点数表达；示例只演示新手任务一次奖励，不默认注册就赠送。 |
| `policies` | 明确有效期、退款处理、扣点顺序和收款路径；`undecided` 只供设计阶段。 |

Schema 检查结构；配置导入方还必须检查：套餐和服务 ID 各自唯一，点数求和不溢出，最终到账点数大于零，版本未被覆盖，主体/渠道绑定合法，未决政策已解决。所有数值都在 JavaScript 安全整数范围内，运算后仍须检查；线上账本可采用数据库整数或十进制整数编码，不能隐式转换现有金额字段。

商品详情须显示总价与币种、购买/赠送点数、适用 Agent、单次服务价格、有效期与退款条款。示例设置“点数不跨 Agent 使用、赠送先扣、一次服务成功才结算”的草案规则；有效期、退款与收款路径留待负责人选择。

## 购买与一次到账

1. Host 从平台读取已发布目录。用户只选择套餐 ID 和版本，客户端自报的金额、点数、创作者和收款账户均不能作为权威价格或路由。
2. 平台校验当前用户和套餐归属，创建不可变的订单快照：用户、创作者、Agent、套餐、币种、价格、购买/赠送点数、政策版本与收款主体。创建前保存幂等编号；同编号异参冲突，不能修改原单。
3. 支付服务依据这个快照生成支付请求；渠道与商户凭据只在平台。当前 SDK 的 `create({ paymentToken, requestKey })` 不能凭空发起此类套餐订单，见[接入分工](integration.md)。
4. 平台验证渠道通知或主动查询结果，核对订单、商户、金额和币种。在同一个耐久事务内，将支付确认为已入账并创建唯一的额度发放记录。重复、并发或乱序事件不重复发点；异步处理用耐久事件和对账补偿恢复。
5. Host 查询平台确认的状态并刷新余额。渠道跳转成功、URL 参数、浏览器 localStorage 或 Agent 的文字均不是发点依据。付款确认前显示确认中；页面关闭仍应可通过原订单找回。

订单状态、支付状态和额度发放状态分别记录。现有 SDK 支付只有 `waiting / processing / completed / closed`，不要在解析器中私增“已发点”或“已结算给创作者”状态。晚到支付确认与过期/关闭事件冲突时交由平台对账，不能静默丢弃已收资金或自动创建第二单。

## 一次服务怎样收费

平台应提供独立于 LLM Gateway 的业务消费合同，适用于工具、MCP、API 和创作者托管的服务。报价、额度预留、结算和释放是待定义的平台能力，不是本 SDK 已有方法。

| 时机 | 业务状态与点数处理 |
| --- | --- |
| 用户发起新业务动作 | Agent 验签并保存请求摘要、原始业务输入和 `operationId`；平台冻结服务版本与本次点数。用户须能看到收费标准。 |
| 准入 | 按主体范围加锁并原子预留点数；可用余额为到账减已消费减仍预留。余额不足不开始业务，保留原请求等待购买。 |
| 开始执行 | 业务先持久化 `running`，底层每次模型/工具调用有各自稳定的 `callId`；不能把每个调用又算成一次服务售价。 |
| 成功 | 先耐久保存可返回的结果和结算意图，再通过可恢复的协调过程结算一次业务消费；确认扣点后对用户完成交付，重复恢复只返回同一结果。 |
| 已知失败且未交付 | 确认未成功后释放原预留点数；重试复用原业务请求与已冻结价格，不能盲目新建调用编号。 |
| 执行结果不明 | 保存 `outcome_unknown`，保留预留与查询路径；先核对底层结果，禁止自动释放后重跑。需有超时升级和人工处理入口，不能永久无提示冻结。 |
| 用户取消或断流 | 停止等待不证明服务端停止；查明未执行才释放，已成功则按事先明示的规则处理。 |
| 成功结果已存但结算确认丢失 | 只重放原消费编号的查询/结算，禁止重跑业务；使用耐久 outbox 或等价机制跨业务库与账本恢复。 |

同一业务动作对应一个服务费，可能对应多个实际模型成本条目。`operationId` 标识原业务动作；`callId` 标识某次收费底层调用；`requestKey` 标识 Host 的支付创建尝试。新业务合同还需平台生成的消费记录 ID，不复用支付 ID 冒充消费 ID。

幂等键至少在“经验证的用户 + 创作者 + Agent + operationId”内唯一；请求摘要或服务 ID 不一致时冲突。赠送与购买点数按确定顺序分配到原额度批次，预留、扣减、释放均留存批次关联，便于之后退款和对账。

## 四类账与创作者收款

| 记录 | 关键内容 | 不代表什么 |
| --- | --- | --- |
| 资金与支付记录 | 法币金额、币种、订单、渠道交易、退款/拒付调整 | 平台或商户收到了充值，不等于服务已完成。 |
| 额度批次与消费账 | 购买/赠送、剩余、预留、消费、过期/撤销、原始批次 | 点数不能作为法币余额或直接提现。 |
| 服务执行与成本 | operationId、结果、消费记录、各 callId 及实际模型/工具成本 | 成本不是创作者向用户收取的服务售价。 |
| 创作者应收与结算 | 服务归属、计价依据、费用、调整、结算单和到账凭证 | 应收不等于已到账；后台显示收入也不是到账证明。 |

两种收款路径只需选一种，**模板不替负责人做选择**：

- `creator_direct`：创作者核验后的商户直接收款。需要订单路由、渠道交易与其到账凭证的对应；统一进程级 merchant 配置不能代替多创作者绑定。仍须管理未消费权益、退款责任和服务履约。
- `platform_collects`：Combo 收款后按约定形成创作者应付款。须确定购买点数的资金分摊、平台费/渠道费/成本承担、促销补贴、退款与拒付、结算周期及舍入规则。最小版可人工支付，但要关联结算单与脱敏到账凭证。

不得默认所有充值立即可分给创作者，也不得把无现金来源的赠送点数按面值计入可结算收入。若赠送消费由平台补贴，需要另有明确的补贴规则和资金来源。总应收、扣除项、已支付与调整后余额要能逐笔核对。具体财务处理由对应主体确认，本 kit 不替代其结算政策。

## 过期、退款与变价

上线前必须在已发布政策中明确：购买与赠送点数各自有效期、过期时间的时区、未使用/部分使用套餐能否退款及计算方法、赠送点数如何撤销、服务失败补偿、退款处理时限与受理渠道。

退款不能只把用户余额减少：关联原资金交易和额度批次，检查已有消费与预留，生成独立调整记录，并同步影响创作者应收/结算。退款过程与消费竞争要锁定同一批次；无法撤回的已付款项进入明确的追偿/调整流程。不得静默删除旧账或修改历史订单的价格快照。

模板的 `undecided` 表示这些商业政策尚未决定，不表示默认不可退款或默认永久有效。确认政策后应版本化扩展目录格式和平台合同，再发布可购买目录。
