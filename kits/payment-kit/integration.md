# 平台、Host、Agent 与 SDK 如何接入

核对基线：SDK `a39f0cc50e9724ec9ef47716c355699380da6f27`，锁定支付协议来自 Combo `84d75d8cc604fd70253bd0598006f92a0f4c9434`。本 kit 没有新增 SDK 运行时导出或线上 HTTP API。平台商业能力增量按 [Combo #357](https://github.com/dangdang-tech/Combo/issues/357) 实现；已有 SDK 的发布与完整接入验收继续按 [Combo #308](https://github.com/dangdang-tech/Combo/issues/308) 跟踪。

## 可以直接复用的部分

| 能力 | 已有入口 | 对这套商业模式的边界 |
| --- | --- | --- |
| 验证当前用户 | `createAssertionVerifier()` / `verifyRequest()`，见[身份接入](../../PAYMENT_SDK_INTEGRATION.md#身份与模型接入) | 不能相信正文自报 userId；新的消费合同也需绑定真实身份。 |
| Agent 独立身份与模型调用 | `createAgentAccessTokenProvider()`、`createLlmClient()` | 模型成本调用可复用；不能借此把每次模型调用变成一次业务服务费。 |
| 识别模型余额不足 | `PaymentRequiredError`、`createPaymentHostMessage()` | 仅对现有合法 402；不等于支持套餐购买或业务点数不足。 |
| Host 支付创建与查询 | [支付客户端](../../PAYMENT_SDK_INTEGRATION.md#host-调用支付中台) `createPaymentClient()` | 创建仅接受 `paymentToken`、`requestKey`；不接受套餐、业务点数或任意金额。 |
| Host 付款后继续 | [host-payment.ts](../../templates/nextjs-agent/lib/host-payment.ts) | 模板源码，非 SDK 导出；需由 Host 提供会话、存储、收银台与恢复。 |
| 保存原任务与成功结果 | [operation-store.ts](../../templates/nextjs-agent/lib/operation-store.ts)、[operation-handler.ts](../../templates/nextjs-agent/lib/operation-handler.ts) | 可参考状态和幂等模式，生产须耐久存储；模板内存存储不是生产实现。 |
| 判断模型失败后能否重试 | `LlmGatewayError.canRetrySameCall` | 只说明该模型调用的受信失败结果；不证明业务点数已释放、整个服务失败或创作者款已撤销。 |

SDK 当前 `Money` 的金额是 CNY 整数分字符串。不要把 `amountCents` 当成点数，不要构造 `PaymentRequiredError` 伪造业务余额不足，不要向三字段 `combo.payment_required` 消息加套餐、金额、网址或业务编号，也不要放宽现有合同解析器。

## 要补的合同，由谁负责

下表是能力合同清单，**不是已经可调用的方法或路径**。发布前需在 Combo 的规范 OpenAPI/锁文件中定义，再同步 SDK 实现和 conformance。

| 待提供的能力 | 输入和权威约束 | 所有者 |
| --- | --- | --- |
| 目录发布/读取 | 受控配置绑定创作者与 Agent；返回不可变版本、价格、点数、政策和适用范围。 | 平台管理面；Host 只读已发布目录。 |
| 主动套餐购买 | 当前用户、套餐 ID、目录版本、稳定幂等编号；服务端冻结金额/收款归属并关联支付。 | 平台订单与支付；Host 选择套餐和查询原单。 |
| 业务点数余额 | 验证身份、创作者/Agent 范围；返回可用、预留及政策需要的购买/赠送分类。 | 平台账本。 |
| 业务准入与消费 | 当前用户、已授权服务、稳定 operationId、原请求摘要；冻结价格、原子预留、一次结算/释放、状态查询。 | 平台账本与 Agent 的耐久业务协调器。 |
| 发放奖励 | 验证完成条件，用户与奖励规则版本唯一；客户端只请求核验，不能自报奖励数。 | 平台。 |
| 创作者收款与对账 | 核验商户或收款归属、应收、调整、结算单、实际到账证明。 | 平台与收款负责人。 |

Agent 不应拿 PSP、商户密钥或平台共享 admin token；SDK 继续无状态。平台保存价格与账，业务保存原始请求、执行状态和结果，Host 保存用户上下文与支付尝试。

## 给编码 Agent 的实施顺序

1. 先读 [AGENT.md](../../AGENT.md)、[支付使用手册](../../PAYMENT_SDK_INTEGRATION.md)及本 kit。记录当前工件 SHA/摘要和合同版本；先完成离线配置与存储设计。
2. 与平台对齐上表能力和收款路径。当前 SDK 没有这些商业接口时，可提交合同与本地 adapter 草案；不要编造 `/packages`、`purchaseCredits()` 等已存在入口，或对真实 `/v1/payments` 添加未经约定的字段。
3. 为业务实现耐久的原请求/状态/结果存储。给通用业务计费提供一个服务端边界，一次 operation 对应一次承诺的交付；底层模型和工具保留独立 callId。用户自己的 Codex 原生推理不自动属于收费边界，不要为了收费重建或强制代理其推理循环。
4. 在平台合同可用后接入身份、报价与预留、执行、保存结果、结算和查询恢复。调用结果不明、结算结果不明分别处理；跨实例竞争由锁、唯一约束与事务保证。
5. Host 接入套餐选择、余额刷新、付款、查询原单和原任务恢复；恢复时取得当前用户的新断言并验证归属。购买可以独立发生，不必伪造一个模型调用来触发 402。
6. 使用[验收表](acceptance.md)交接，分别提供模拟、Test、真实交易与创作者到账证据；合同可用前只能报告设计/离线实现进度。

## 用户界面需要表达的状态

| 情况 | 建议文案与动作 |
| --- | --- |
| 选择服务 | 显示“本次消耗 2 点，可用 8 点”，高级服务显示自己的价格；实际值来自平台。 |
| 额度不足 | 显示缺口与套餐，保留原任务；用户也能独立购买后再开始服务。 |
| 支付正在核验 | 显示“正在确认付款”，查询原单，不让用户重新买一笔。 |
| 已确认发点 | 显示到账和最新余额，允许按当前身份继续原任务。 |
| 服务执行中或结果不明 | 显示处理中/结果待确认及查询入口；不要把它显示成支付失败。 |
| 业务失败且确认释放点数 | 显示未收取本次服务点数及是否可以重试；底层成本是否产生由创作者账单另记。 |
| 结果已保存但结算未确认 | 显示正在确认本次服务，查询原消费；不再次执行。 |

价格、政策和文案应随受信目录配置。不要把合同、内部 token 或开发检查项暴露在面向用户的付款流程中。
